# Архитектура

## Реализовано

- `Store`: миграции версий 1–7 в транзакции, foreign keys, WAL, участники, встречи, очередь и экспорт метаданных.
- CLI и локальный HTTP-адаптер используют одни операции Store.
- Уникальный индекс запрещает несколько активных заданий транскрипции одной встречи.
- Повтор разрешён только для failed-заданий; число попыток сохраняется.
- Веб-панель не запускает запись и не выдаёт фиктивные результаты моделей.

## Предстоящие контракты

Контракты ниже — целевые интерфейсы; текущее состояние захвата и хранения уточняется далее.

- AudioSource: обнаружение устройств, start/pause/resume/stop, события уровня и ошибок. Swift-адаптер экспортирует C ABI для Rust, не вызывает ML из audio callback.
- RecordingStore: ограниченная очередь фрагментов, независимый writer, контрольные суммы и восстановление. Исходное аудио неизменяемо при повторном анализе.
- SpeechBackend: аудиофрагмент + версия модели + параметры → сегменты с началом/концом, текстом, источником и статусом preliminary/final. Whisper.cpp использует Metal на Mac.
- DiarizationBackend: интервалы речи → временные speaker_id. Конкретная модель пока не выбрана; выбор требует проверки качества русского аудио, лицензии и запуска на Mac.
- SpeakerIdentifier: речевые образцы → эмбеддинги с версией модели; сопоставление с порогом уверенности либо unknown. Регистрация требует сведений о согласии.
- Worker: устойчивое получение задания, lease/recovery, попытки и версии результатов. Сейчас существует только хранение очереди.
- Events: meeting_id, source_id, model_run_id, revision и временные метки. UI и будущая LLM получают события вне потока записи.

## Веб-панель

Текущий сервер синхронный и предназначен для лёгких операций управления. Тяжёлые модели в HTTP-обработчиках запускать нельзя. API v0: GET /api/status, /api/people, /api/meetings, /api/jobs; POST /api/people {name}, /api/meetings {title}, /api/jobs {meeting_id}. Данные выводятся как текст, не как пользовательский HTML. Настройки моделей, устройств и нагрузки добавляются вместе с соответствующими реализациями и валидацией.

## Границы платформ

Rust: application core, SQLite, очередь, CLI, HTTP и управление вычислениями. Swift: разрешения и захват macOS (системный звук через ScreenCaptureKit позже). C++: готовый inference backend Whisper.cpp через FFI. LLM не обязательна для записи и распознавания.

## Слой WAV

`audio.rs` реализует приём завершённых WAV без вызова моделей. Публикация через hard link и fsync предшествует регистрации в SQLite; это позволяет повторно индексировать файл после прерывания. Идентичность определяется SHA-256, уникальность — пара meeting_id/sha256. Хранилище должно принадлежать приложению; незавершённые файлы и повреждённые контрольные суммы не импортируются автоматически. При восстановлении ошибка возвращается явно; уже зарегистрированные корректные фрагменты сохраняются. Начальная ограниченная очередь и потоковый writer теперь подготовлены в Swift; аппаратная проверка остаётся обязательной.

Swift-пакет в native/macos управляется сервером через дочерний процесс. FFI не используется. Проверка его сборки и поведения на macOS остаётся обязательной.

## Управление записью (текущая реализация)

`CaptureManager` принадлежит процессу `serve`. HTTP POST /api/recording/start {meeting_id,seconds} запускает дочерний процесс адаптера; POST /api/recording/stop {meeting_id} отправляет `stop` в stdin. CLI meeting start/stop обращается к этим локальным endpoint. GET /api/status содержит recording.available, active и last. Доступность означает наличие файла адаптера, а не проверенные разрешения микрофона.

Протокол: аргументы адаптера — пустой каталог сессии и лимит секунд. `READY\n` в stdout подтверждает начало захвата; stdin `stop\n` либо EOF завершает запись. Завершённые WAV публикуются последовательно и импортируются Rust во время записи; выход 0 после READY считается успехом только при наличии хотя бы одного фрагмента, без пропусков и незавершённого хвоста. Ошибка не создаёт фиктивную запись БД. stderr наследуется сервером; аудио и текст речи туда не выводятся. stdout дочернего процесса считывается отдельным потоком. HTTP-цикл опрашивает завершение каждые 100 мс без ожидания всей записи. Ожидание разрешения ограничено 90 секундами, остановки — 10 секундами; при превышении процесс принудительно завершается, staging-файл сохраняется для проверки.

SQLite атомарно резервирует встречу и запрещает второго владельца записи. Если процесс сервера прерван, состояние recording может остаться в БД. Оно снимается только явной операторской командой meeting recover после проверки отсутствия активного захвата. Автоматически считать все recording-встречи аварийными при открытии БД нельзя: CLI и сервер используют одно хранилище.

Предыдущее описание Swift как автономного инструмента относится к начальному этапу: теперь он управляется сервером. FFI по-прежнему отсутствует. Непрерывное разбиение на фрагменты подготовлено в Swift, аппаратная валидация macOS остаётся обязательной.


## Потоковое сохранение фрагментов

Swift AVAudioEngine захватывает непрерывный поток. Callback копирует PCM в один из максимум 32 ожидающих буферов; запись на диск выполняется в отдельной serial queue. При переполнении захват явно завершается с ошибкой, завершённые фрагменты сохраняются. Writer нарезает поток по числу кадров (5 секунд при частоте микрофона) без перезапуска устройства. `.partial.wav` становится `NNNNNN.wav` только после закрытия WAV и синхронизации; при остановке завершается короткий хвост.

Rust каждые 100 мс проверяет очередной ожидаемый номер и индексирует максимум 4 фрагмента за итерацию HTTP-цикла. Порядок не зависит от stdout: READY подтверждает захват, файлы являются устойчивым журналом завершённых фрагментов. SQLite v3 хранит capture_fragments отдельно от content-addressed recordings. Каждый фрагмент имеет session_id, sequence, ссылку на WAV и start_frame. Последовательность непрерывна, частота и число каналов неизменны в рамках сессии. Повтор одинакового WAV не удаляет его повторные появления на временной шкале.

После сбоя исходные каталоги сессий позволяют повторно построить эту шкалу. Recovery идемпотентен, не выполняется для активной встречи и сообщает о разрыве последовательности. Частично записанные WAV автоматически не ремонтируются. Сохраняемые staging-копии требуют дальнейшей политики хранения. Необходимы проверки реального AVAudioEngine: формат устройства, нагрузка writer, дисковые ошибки, отключение устройства и двухчасовой прогон.


## Post-Meeting Whisper backend

`speech.rs` использует закреплённый CLI Whisper.cpp через отдельный процесс. SQLite v4 добавляет model_runs и segments. Claim pending-задания и увеличение attempts выполняются транзакционно. Одновременно разрешён один running-worker; запись и Post-Meeting inference взаимно исключены. Тяжёлая работа не выполняется в HTTP-процессе.

До обработки проверяются SHA-256 исходных WAV. FFmpeg нормализует каждый уникальный WAV до mono PCM16/16 kHz; Rust объединяет все появления в правильном порядке и пересчитывает смещения по фактическому числу нормализованных кадров. Whisper получает язык (ru по умолчанию), до 4 потоков, JSON-выход. Парсер проверяет offsets в миллисекундах и сопоставляет сегменты с интервалами исходных фрагментов. Успех model_run, сегменты и завершение задания фиксируются одной транзакцией; ошибка сохраняет failed и не заменяет прежнюю успешную версию.

Для воспроизводимости сохраняются SHA-256 модели и исполняемого файла движка, язык и входной manifest. Просмотр показывает последнюю completed-версию; истории прежних версий в UI пока нет. Идентификаторы говорящих и ручные исправления ещё не реализованы.

CLI: jobs run, jobs recover ID, meeting transcript ID. HTTP: POST /api/jobs/run {}, GET /api/transcript/ID; состояние worker — в speech объекта /api/status. Запуск через панель создаёт самостоятельный процесс vtracker jobs run. Если сервер закрыт, worker может завершиться самостоятельно; статус задания остаётся в SQLite. Автоматического lease recovery нет.

Локальные stdout/stderr inference-процессов не транслируются в журналы, чтобы не выводить текст речи. Таймаут FFmpeg — 300 сек на уникальный вход, Whisper — 7200 сек. Диагностика сообщает код завершения и путь инструмента без транскрипта. После публикации среды модель multilingual tiny загружена с проверкой upstream checksum. Реальный тест на английском JFK прошёл на Linux CPU; русский язык и Metal остаются непроверенными. Silero VAD подключён опционально; потоковое распознавание ещё не реализовано, диаризация подключена отдельным опциональным backend.


## Опциональный VAD

SpeechConfig принимает `VTRACKER_VAD_MODEL`. Если значение задано, файл проверяется и в CLI Whisper.cpp передаются `--vad -vm` с явными параметрами сегментации. Ошибки модели не подменяются режимом без VAD. SQLite v5 добавляет model_runs.parameters_json: число потоков, нормализованный формат, параметры VAD, путь и SHA-256 модели. Эти параметры доступны в транскрипте; у прежних версий параметры остаются {}.

Реальный тест подтвердил обработку тишины и сохранение смещения после добавленных 3 секунд тишины. На трёх русских FLEURS-фразах tiny без VAD дал WER 7/44, а с VAD — 15/44. Поэтому VAD не включается автоматически; настройка и выбор STT-модели требуют отдельного репрезентативного корпуса.

## Следующий движок говорящих

Исследован кандидат sherpa-onnx: опубликованный C++ API OfflineSpeakerDiarization разделяет segmentation, speaker embeddings и clustering. Это соответствует самостоятельному backend рядом с Whisper и допускает C/C++-адаптер для Rust. До подключения нужны закрепление версии, проверка лицензий конкретных моделей, сборки на Apple Silicon и качества на русском многоголосом аудио. Для первой интеграции выбраны Pyannote segmentation 3.0 и WeSpeaker VoxCeleb ResNet34; кластеры реализованы, голосовые профили и имена ещё нет. Смена говорящего и сопоставление с именем остаются разными задачами.


## Реализованный backend диаризации

Rust DiarizationConfig управляет внешним C++-адаптером native/diarization/main.cpp, который использует C API sherpa-onnx v2.0.1 и CPU ONNX Runtime. Дополнительного Python runtime в контуре обработки нет. Helper принимает модели, mono WAV 16 kHz, путь JSON и известное число голосов (0 для auto). Артефакты закреплены версиями и upstream SHA-256.

SQLite v6 добавляет speaker_turns, связанные с model_run_id. После Whisper последовательно запускается диаризация; оба результата публикуются атомарно. Ошибка любого backend переводит задание в failed, сохраняя прежнюю успешную версию. Параметры кластеризации и fingerprints входят в parameters.diarization.

Parser проверяет положительные интервалы, границы записи и допустимые ID кластеров. Временное перекрытие разных голосов допустимо. Attribution считает объединённое перекрытие интервалов одного кластера с текстовым сегментом. Единственный кластер назначается только при >=50% покрытия; несколько кластеров дают multiple и null speaker_id, слабое или отсутствующее покрытие — unknown. Это эвристика временного сопоставления, не уверенность распознавания личности. Текст не делится между голосами без временных меток слов.

Реальная интеграционная проверка автоматически получила 2 кластера / 4 интервала из официального двухголосого английского примера. Проверки с фиктивным backend отдельно подтверждают атомарность, сохранение прежней версии при ошибке, множественные голоса и отсутствие двойного подсчёта перекрытий. DER, русский многоголосый корпус и Apple Silicon остаются непроверенными.


## Ручное сопоставление с людьми

SQLite v7 добавляет append-only speaker_assignments. Каждое событие хранит model_run_id, speaker_id, person_id (либо null для снятия связи) и время. Назначить можно только существующего говорящего завершённой версии и существующего человека. Текущая связь — последнее событие этого run/cluster; история не перезаписывается. Результаты моделей остаются отдельными.

Transcript накладывает имена на интервалы и кандидатов, а на целый текстовый сегмент — только при наличии single speaker_id. При нескольких голосах неопределённость сохраняется. Повторная обработка получает новый run и не наследует связи по совпадению speaker_N. CLI, API и панель используют общую операцию Store.assign_speaker.

## Рабочее пространство и новая веб-панель (SQLite v8)

По уточнению пользователя первым интерфейсом остаётся веб-панель. SwiftUI не подменён браузерной имитацией: нативная оболочка отложена, сервисная граница вынесена отдельно (`web/service.mjs`). `workspace.rs` владеет проектами, задачами, историями, предложениями, решениями и настройками. Интерфейс получает общий snapshot через GET /api/workspace и отправляет транзакционные команды POST /api/workspace/action. Разные представления не хранят собственных копий задач.

Даты рассчитываются ядром с chrono/chrono-tz. Дата без времени завершается при первом допустимом моменте следующего локального дня; для повторяющегося явного времени используется позднее вхождение, несуществующее явное время отклоняется. Завершённость определяется системным типом этапа проекта, блокировка — независимый признак. UI-фильтры/доска/обзор используют одни функции domain.mjs и готовые флаги сроков из ядра.

SQLite хранит JSON-поля сущностей с revision и отдельными change_events. Проверка revision предотвращает потерю чужого изменения. Массовое действие и undo выполняются транзакционно; undo запрещён при последующих правках. Изменение пайплайна с занятыми этапами требует явной карты переноса и откатывается целиком при ошибке.

Предложения находятся отдельно от tasks. Только review создаёт/изменяет задачу, добавляет источник существующей задаче или фиксирует решение. В демо origin=demo_ai, в реальном ручном сценарии origin=manual. Регистрация из голоса и автоматическое назначение ответственного не выполняются.

Демо изолируется флагом is_demo и проверкой ссылок между режимами. Набор создаётся один раз, не сбрасывает правки. Clock инъецируется в workspace/seed_demo_at для тестов; плановые даты используют одну опорную дату. UI-состояние секции/фильтров/инспектора сохраняется в localStorage, рабочие настройки и данные — SQLite.

API аудио поддерживает Range и не принимает произвольный путь файла. Импорт потоково ограничен 256 МБ; преобразование FFmpeg выполняется после записи. Закрытие вкладки не влияет на дочерний процесс микрофона. Протокол адаптера сообщает READY, CAPABILITIES, LEVEL, ERROR; старые адаптеры не получают неподдерживаемую паузу. Авто-STT запускается сервером после завершения, независимо от открытого экрана. UI показывает отдельные состояния записи и обработки, а при ошибке — длительность действительно сохранённых фрагментов.

Поддержка паузы/уровня добавлена в Swift, аппаратная проверка Mac не проводилась. Реальные LLM и Live STT отсутствуют; соответствующие функции не выдаются за работающие.


## Выбор устройства и проба микрофона

Адаптер macOS публикует `--devices` (JSON: id, uid, name, isDefault), принимает необязательный стабильный UID третьим аргументом записи и поддерживает `--test SECONDS [UID]` без аудиофайлов. CoreAudio ID разрешается заново из UID; выбранное устройство устанавливается только для процесса захвата, системная настройка не меняется. Протокол расширен сообщением `DEVICE\t{…}`; source.json в staging позволяет восстановить метаданные после падения сервера. Миграция 009 добавляет capture_sources; JSON-экспорт фрагментов включает device. Старые фрагменты возвращают null.

GET /api/devices обновляет список; POST /api/devices/select сохраняет UID; POST /api/devices/test запускает ограниченную проверку уровня. Статус доступен в /api/status → microphone. Проверка и запись взаимно исключены. Успешное перечисление устройств не означает выданного разрешения: оно запрашивается только при явном начале захвата/теста. CLI devices list/test работают без открытия БД.


## Локальный Live STT (миграция 010)

`live_sessions` задаёт версию предварительной обработки; `live_chunks` ссылается на сохранённые capture_fragments и хранит статус, предварительные сегменты, SHA-256 модели/движка и время обработки. Повторяющиеся одинаковые WAV остаются отдельными событиями с правильными таймкодами. Финальные model_runs/segments независимы. JSON-экспорт включает live; CLI `meeting transcript ID --live` читает этот снимок.

Сервер сначала обслуживает capture.poll, затем ставит ссылки на завершённые фрагменты в очередь. Один Live-процесс (`live-chunk`) обрабатывает один WAV через FFmpeg и whisper-cli, с nice +10 и двумя потоками CPU. Промежуточные файлы принадлежат временному каталогу родителя. Предварительное декодирование — greedy best_of=1 без temperature fallback; финальное сохраняет прежние параметры. Включённый VAD передаётся движку. Диаризация отложена до итоговой обработки.

Одновременно допускаются не более четырёх pending/running фрагментов и один ML-обработчик. При переполнении или двух последних медленных фрагментах (более 1,5 длительности аудио) Live откладывается до окончания встречи. Таймауты: FFmpeg 10 с, Whisper 20 с, внешняя защита процесса 35 с. Ошибка Live не распространяется на CaptureManager; полная запись доступна для повторной обработки. Это ограничение очереди и адаптация по скорости, а не полноценный монитор RAM/CPU/GPU.

При остановке новые Live-задания не запускаются, оставшиеся pending откладываются; текущий процесс завершается до старта финального. Drop LiveWorker завершает его группу процессов. После аварийного завершения статус running требует явного операторского восстановления после подтверждения остановки старых процессов (POST /api/live/recover). Автоматический перехват lease не реализован.

Для изолированных проверок VTRACKER_PORT задаёт отдельный loopback-порт (по умолчанию 8765); Host/Origin проверяются относительно этого порта. scripts/live-smoke.py использует это для теста без изменения рабочей БД.


## Дополнение частей встречи и регистрация голоса

Миграция 011 добавляет audio_timeline с отдельным событием на каждое вхождение WAV. Миграция сохраняет прежний порядок; новые импорты и части добавляются в конец. CaptureManager.continue_device разрешает продолжение completed/failed встречи с аудио, запрещает запись при pending/running обработке. Старые model_runs не меняются; экспорт отмечает transcript.needs_update, пока число входных событий не совпадает с последним завершённым проходом. API recording/continue и CLI meeting continue используют тот же контроль владения записью.

Миграция 012 добавляет voice_consents, voice_jobs, voice_samples и voice_profiles. Регистрация из файла требует согласия local-voice-v1 и подтверждения одного голоса. Предельный размер 16 МБ, нормализованная длительность 6–60 с, проверяются RMS, audible fraction и clipping. Проверка техническая, не биометрическая верификация. VoiceWorker в отдельной группе процессов использует CPU 2 threads и sherpa-onnx C API; модель и движок фиксируются SHA-256. Старые версии профиля не перезаписываются. Модели разных SHA-256 не объединяются.

HTTP status отдаёт только метаданные профиля/задания, без эмбеддингов и путей образцов. Каталог voice рядом с БД имеет права 0700. Регистрация не использует облачное распознавание. Удаление файлов и строк профилей не удаляет people/встречи/ручные назначения. Согласия отмечаются отозванными. Это удаление из приложения, а не гарантия физического стирания из SQLite WAL, накопителя или резервных копий. Шифрование и политика резервных копий остаются незавершёнными требованиями раздела 9 ТЗ.

Прямая запись образца, извлечение из неизвестного говорящего и автоматическое сопоставление с порогами неизвестного ещё не реализованы. Проверка реального SDK на публичном аудио: docs/voice-validation.json.


## Регистрация из встречи и голосовое сопоставление (013)

voice_jobs.source_json и voice_consents.source_json фиксируют тип источника, model_run_id, speaker_id и интервалы согласованного образца. План берётся только из завершённой реальной версии, объединяет интервалы одного голоса, вычитает перекрытия остальных, отбрасывает участки короче 800 мс и выбирает наиболее длинные до общей длительности 30 с. Нужны минимум 6 с. В API предпросмотра возвращаются только таймкоды. Сборка WAV выполняется фоновым VoiceWorker по immutable inputs_json выбранного прохода с проверкой SHA-256 исходных WAV.

voice_match_jobs хранит модель обработки, состояние и снимок порогов; voice_matches — отдельные кандидаты/неизвестные с версией профиля, сходством и причиной. Результат не пишет speaker_assignments. Ручное назначение и ручной unknown подавляют подсказку; segment_assignments имеют приоритет над назначением голоса. Результаты относятся только к конкретному model_run_id. Новый неуспешный проход сопоставления не скрывает последний завершённый результат.

Сравниваются нормализованные векторы актуальных профилей того же SHA-256 модели, с действующими согласиями и подходящей размерностью. Начальные cosine threshold=0.75, margin=0.10 требуют калибровки; это не вероятность идентификации. До 16 голосов на один проход, остальные явно unknown. Нет совместимых профилей, короткий/плохой образец, низкое сходство или недостаточный отрыв дают unknown, не угадываемое имя. Постоянный профиль неизвестного говорящего не создаётся; временные векторы остаются в каталоге фонового задания до его очистки.

В очередь VoiceWorker объединены enrollment/matching с приоритетом регистрации; одновременно один голосовой, STT или Live-обработчик. Нормальная запись не запускает matching. Автоматическая постановка отключена по умолчанию и выполняется только после успешного коммита итогового транскрипта, при наличии профилей и говорящих. Ошибка постановки не меняет completed на failed. Есть повтор и подтверждаемое восстановление после сбоя; status.voice.interrupted обнаруживает оставшийся running в БД без текущего дочернего процесса.

API: POST voice/source (предпросмотр), voice/from-meeting (регистрация с consent/single_speaker), voice/match, voice/match/retry, voice/matching/settings. В status.voice_data находятся только метаданные заданий/профилей/порогов, без эмбеддингов. В transcript.voice_matches и segment.voice_suggestion содержатся предложения. Удаление биометрии удаляет относящиеся к ней неподтверждённые подсказки, ручные speaker_assignments остаются.

Функциональная проверка: scripts/voice-matching-smoke.py; docs/speaker-matching-validation.json. STT/диаризация в ней — протокольные fixtures, эмбеддинги — реальные ONNX. Качество на разных участниках, русском языке, микрофонах и ложные совпадения пока не измерены.
