# План развития VTASK и Валли

Рабочая база — `v0.1.0-rc.1`. Ветка рекомендаций аналитика — `feature/analyst-roadmap`. Параллельная разработка ведётся в `feature/meeting-changes`.

## 1. Версия 0.2.0 · Изменения после встречи

Цель выпуска — после встречи руководитель видит, какие данные изменятся, и может проверить каждую договорённость по протоколу.

### 1.1. Связать предложение с задачей

- [ ] Завершить подбор существующих задач и проверить его в интерфейсе. Первый вариант уже добавлен локально.
- [ ] Учитывать явно указанный проект и проект встречи. Показывать проект у каждого совпадения. Для встречи о нескольких проектах выбирать привязку отдельно для каждого предложения.
- [ ] При одном совпадении предложить связь. При нескольких дать выбрать. При отсутствии совпадений предложить создание задачи для нового поручения или ручной выбор для изменения существующей задачи.

**Приёмка.** Проверить одно совпадение, одинаковые названия в двух проектах и отсутствие совпадений.

### 1.2. Показать и подтвердить изменения

- [ ] Собрать на экране «На подтверждение» предложения по встрече с группировкой по проектам. Показать новые задачи, изменения сроков, исполнителей и статусов, решения и блокировки.
- [ ] Для выбранной задачи вывести текущее и предлагаемое значения. Добавить переход к встрече и исходной реплике. Срок проверять вместе со временем.
- [ ] Дать исправить предложение перед применением или отклонить его. Если задача успела измениться, показать актуальные данные перед повторным подтверждением.
- [ ] Проверить, что в истории задачи видны результат и источник изменения.

**Приёмка.** Изменить срок с временем, сменить исполнителя и зарегистрировать блокировку через согласование. Открыть исходную реплику и сверить историю задачи.

### 1.3. Повторный анализ и продолжение встречи

- [ ] Проверить, как существующая защита от дублей работает после редактирования расшифровки и после добавления новых реплик.
- [x] На время тестирования заменять неподтверждённые предложения Валли по встрече после успешного анализа. Сохранять подтверждённые изменения, ручные предложения и прежнюю очередь при ошибке анализа.
- [ ] Согласовать постоянные правила объединения новых результатов с очередью.
- [ ] Отличать повтор той же договорённости от новой договорённости по той же задаче, например переноса на другую дату.

**Приёмка.** Повторно обработать одну встречу. Убедиться, что очередь обновилась, подтверждённые изменения сохранены, а сбой анализа оставляет прежнюю очередь доступной.

### 1.4. Пакетное согласование и следующая повестка

- [ ] После проверки отдельных предложений добавить подтверждение выбранной группы. Показать, какие пункты применены и какие требуют проверки.
- [ ] Составлять черновик повестки из открытых вопросов, блокировок и незакрытых задач проекта. Ссылаться на исходные встречи и задачи.

**Приёмка.** Подтвердить выбранные пункты и подготовить повестку следующей встречи на основе подтверждённых данных.

### Состояние реализации

На ветке реализованы подбор задачи, фильтрация согласования по встрече, группировка по проектам, сравнение полей, переход к реплике, сохранение черновиков, защита от повторов и пакетное применение. Пакет применяется целиком. Если один пункт конфликтует с текущим состоянием, приложение показывает причину, и пакет можно пересобрать. Черновик повестки открывается в итогах встречи с проектом. Пункты приёмки ниже остаются открытыми до проверки на Mac.

### Второе ТЗ аналитика · задачи и решения между встречами

Сценарий одного проекта готов к ручной приёмке. Валли подбирает задачу, объединяет срок и исполнителя, связывает утверждённое решение с несколькими задачами и подбирает действующие решения для следующей встречи. Доступны кеш анализа, локальный разбор явных команд, дневной и месячный лимиты токенов. [Описание реализации](docs/wally-analysis.md).

- [ ] Привязка каждого результата к своему проекту, если на одной встрече обсуждали несколько проектов.
- [ ] Связь новой работы с исходной задачей из обсуждения, например проверки склада с существующей закупкой. Выборочные ссылки на материалы и историю связанных задач.
- [ ] События уведомлений после успешного применения решения.
- [ ] Постоянные правила обработки неподтверждённых предложений при повторном анализе.
- [ ] Ручная приёмка на двух реальных встречах с проверкой истории, календаря, Ганта, дублей и фактического расхода токенов.

### 1.5. Приёмка выпуска

- [ ] Пройти полный цикл на Mac от записи встречи до обновления задачи, истории, календаря и Ганта.
- [ ] Проверить обновление с рабочей базой и установку на чистом Mac. Подготовить сборку и описание выпуска по результатам проверки.

## Порядок работы

Начинаем с трёх сценариев версии 0.2.0: одно совпадение, несколько совпадений и повторный анализ. Ведём статус выпусков в [журнале версий](CHANGELOG.md). Базовая работа с проектами и задачами опирается на локальное ядро Rust и SQLite. Порядок этапов задаёт приоритеты, даты выпуска определяем после приёмки.
